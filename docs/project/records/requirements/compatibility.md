# GPT 兼容插件的提供商绑定与会话热切换

## 目标与范围

探索由 DSH 自己运行 Agent 循环、向 GPT 提供 Codex 风格工具与协议的兼容插件。用户希望减少在 DSH 中嵌套整套 Codex 的必要性。本项目独立维护 GPT 兼容路线；现有 Codex Runtime 保留其原有职责。本文是从原地图迁入的权威需求，调研结论不等于功能已经实现。

## 已确认要求

- 在模型设置中绑定提供商的稳定身份及适用模型范围。
- 选择匹配模型时，为当前会话启用兼容工具、提示词和相应提供商适配；选择未绑定提供商时恢复普通 DSH 配置。
- 允许 GPT 与其他模型的会话同时运行，工具可见性和启停不能互相影响。
- 当前请求及其工具结果使用同一套约定，模型切换从下一安全步骤生效；卸载须收尾已有执行并撤销作用域注册。
- 保留 DSH 的权限、审批、日志和任务管理。
- 原生压缩先参考现成开源实现；兼容范围以实际 CPA 部署与端到端结果为准。
- 原生加密压缩与通用文字压缩各自保存、独立触发；匹配的 GPT 路线只使用原生检查点，其他路线只使用通用上下文。两者以同一份原始历史为依据，不互相注入压缩产物。

## 已确认的工具与历史适配原则

文件编辑由插件注册符合 Codex 约定的新工具，在匹配会话中隐藏冲突的 DSH 编辑入口。命令与长进程若难以映射，可以在插件内提供独立实现。两者都应保持工具行为、结果及状态语义完整，而不只更换名称。

这里的隐藏针对模型可见和可调用的旧入口。用户已确认保留底层文件、进程等服务，其他 DSH 插件继续使用这些服务；新工具应通过正式执行链接入。隐藏后的旧工具不能再被包装器当成同作用域内仍可调用的入口，应复用底层服务或设计明确的内部接口。

历史重放先核对并补齐 DSH 已有元数据处理；语义不一致或无法扩展的部分，由新适配实现承担，并按提供商与模型路由。不预设当前实现全部失效，也不为保留原实现而勉强转换不等价的协议状态。

允许按需要补齐宿主的通用插件扩展点，包括工具声明与呈现、提供商协议状态、压缩检查点及模型切换。具体改动与插件构建工具的影响尚待设计；此处不承诺完全零宿主改动。

## 原生压缩的调研依据

截至 2026-09-16，OpenAI 官方文档区分普通 Responses 请求中的服务端压缩和独立 `/responses/compact` 接口；独立接口返回的整个上下文窗口应原样用于后续请求。Codex 后端的 `compaction_trigger` 流程须单独核对，不可由“普通对话可用”推断其受支持。

可借用的实现：

- [partment/opencode-openai-compact](https://github.com/partment/opencode-openai-compact)：提供商配置、压缩触发、检查点持久化与后续请求注入；本轮查阅源码提交 `58d892ee19c89f4ae13fcf068683e63db942d3df`。
- [josevelaz/opencode-codex-native-compaction](https://github.com/josevelaz/opencode-codex-native-compaction)：Codex 订阅后端的原生检查点插件，明确标为实验性。其跨提供商切换只发送检查点后的消息，不能直接满足完整历史接续；本轮查阅 README 提交 `d371e27a532da77526e5c43b9dad8433b8c43d74`。
- [OpenCode V2 压缩文档](https://opencode.ai/v2/docs/compaction)：原始历史持久保存，原生检查点按提供商、模型、协议和端点匹配，不兼容时回到可用检查点或保留历史。适合借用此分离方式。

## 已确认的两版压缩与独立触发

用户先提出同时维护两版压缩，随后明确不必同时执行。最终要求是两种上下文表示独立保存、独立决定何时压缩，不在每次 GPT 压缩时强制再生成一份通用摘要。本节替代上一版“通用摘要生成时机尚未决定”的候选说明。

DSH 保留完整原始历史作为共同依据。每个压缩检查点记录所覆盖的原始历史边界、保留项及适用范围；后续请求由该路线的检查点及边界之后的新历史组成，避免遗漏或重复。

| 上下文路线 | 压缩结果 | 使用范围 | 触发条件 |
|---|---|---|---|
| 原生路线 | OpenAI 返回的完整压缩窗口，包含加密检查点及必要保留项 | 已绑定且与检查点兼容的 GPT 提供商、模型、协议与端点 | 按该路线实际请求预算提前触发 |
| 通用路线 | DSH 管理的可读文字摘要及保留历史 | 其他提供商、未绑定路线，以及插件停用后的普通 DSH 上下文 | 按目标模型实际请求预算独立触发；无需随原生路线一起压缩 |

用户举出的 GPT 256k、其他模型 1m 作为其当前配置的场景记录，不写成所有 GPT 或其他模型的固定容量。实现读取所选模型与提供商的有效上下文配置，并计入系统提示、工具声明、待发消息和输出预留；不等到容量耗尽才处理。

第一次切换到其他模型时，若没有通用检查点且原始历史在预算内，直接构造普通上下文即可；超出预算才生成通用摘要。已存在通用检查点时，必须加上此后所有有效的新历史，不能把旧摘要当成完整当前状态。通用路线的压缩边界可以晚于或早于原生路线。

切回 GPT 时，同样在兼容的原生检查点之后接入新增历史，包括在其他模型下完成的工作；先转换成目标协议接受的普通消息和成对工具记录，排除其他提供商专用的签名与压缩控制项。原生检查点失效或没有兼容记录时，从共同原始历史重新构造或生成原生检查点，不使用通用压缩产物替代它。

如果在较大窗口模型下积累的新历史超过 GPT 可用窗口，不能一次性把旧原生检查点与全部新增历史交给 GPT。需要按原始历史顺序、完整工具交互边界分批接入，并在必要时逐步生成原生检查点，直至覆盖切换时的历史位置；没有兼容检查点时也沿此流程从可重建的原始记录开始。每次实际压缩输入必须在所选模型预算内，无法处理的单个过大条目应明确报告或按已有输出限制策略处理，不能静默丢弃。切回可能产生多次原生压缩调用及等待，成本和耗时须进入后续评估。

原生加密检查点不传给其他模型；通用压缩摘要及其内部控制消息不注入 GPT 原生路线。正常用户消息、助手结论和工具结果属于共同工作历史，不因来自另一模型而被整体丢弃。插件停用后，原始历史与通用上下文的读取必须仍可用。

每条路线只在生成、校验并持久化成功后替换自己的活动检查点。一条路线失败不能覆盖另一条路线或删除原始记录，也不能静默用另一种压缩产物混入当前模型请求。

这里“本地压缩”指由 DSH 管理的通用摘要流程与存储，不预设摘要模型运行在本机或不产生 API 费用；摘要执行器可配置。容量较大而尚未需要摘要的路线不强制产生额外摘要调用。

当前 DSH `CompactionEngine` 每个上下文提供一个压缩服务，基础实现将活动历史区间替换为摘要节点。实现两版独立上下文需要检查点选择与请求投影的扩展，不能只让两个压缩器先后改写同一个活动摘要。准确扩展点与兼容迁移仍待实现设计。

## 验收与未验证项

1. 两个并发会话分别选择绑定和未绑定模型，工具列表、提示词、执行入口与切换互不影响。
2. 新编辑工具可完成创建、修改和删除，失败信息正确；旧编辑入口在对应会话不可调用，其他会话不受影响。
3. 长进程句柄、输出增量、退出、取消、切换和卸载均有明确归属；不得静默丢失执行。
4. 以用户实际 CPA 版本及端点验证“压缩成功 → 保存 → 下一轮继续 → 重启恢复”，并检查特殊输入输出项未被代理转换丢弃。
5. 切换其他提供商、再切回、停用插件后，历史仍可恢复；不把不兼容检查点交给目标模型。
6. 原生路线已多次压缩、通用路线尚未压缩时，切换后仍可从原始历史接续；不同路线的边界不要求相同。
7. 在 256k 与 1m 的受控配置下验证独立触发、提示与工具等预算预留；断言 GPT 请求不包含通用压缩产物、其他模型请求不包含原生加密检查点。
8. 在其他模型下继续工作后切回 GPT，新增消息与工具结果既不丢失也不重复；旧检查点不能使会话回到旧进度。
9. 覆盖一侧压缩失败、重启、插件停用和检查点不兼容；另一侧已保存状态与原始历史仍完整。
10. 在大窗口模型下新增超过 GPT 单次预算的历史后切回，验证分批原生压缩接续、完整工具边界与失败恢复；每次请求均在预算内且未使用通用摘要替代。

当前没有进行真实 API 调用、插件安装或上述运行验收。CPA 按 CLIProxyAPI 理解，具体部署版本尚未核实。

CPA 当前公开源码提交 `8335eac731946bd4eff18f500653f93736df53d6` 的 Codex executor 包含独立 `/responses/compact` 路径；这不证明用户部署支持全部压缩协议。[问题 #4848](https://github.com/router-for-me/CLIProxyAPI/issues/4848)报告的是 7.2.121 双层代理链中的 v2 压缩输出丢失，不能泛化成所有 CPA 版本均有此故障。

官方依据：[Compaction](https://developers.openai.com/api/docs/guides/compaction)、[Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)。本轮完成的是需求保存与只读调研，性能和任务完成质量收益仍需后续评估。
